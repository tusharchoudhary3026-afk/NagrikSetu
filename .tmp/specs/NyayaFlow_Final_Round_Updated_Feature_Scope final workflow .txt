1. Case framing and corrections
<b>Case context.</b> The case describes grievances arriving through at least four channels and partially separate workflows,
complaints in English/Hindi/Hinglish, generic status labels, and a simulated finding that 23% of grievances were reassigned at
least once. This does not establish that 23% were misrouted or explain why reassignment occurred.
<b>Selected problem statement</b>
How might municipal grievance teams identify and separate multiple issues within one complaint, recommend
responsible departments with grounded evidence, handle unclear or overlapping ownership, and maintain an
auditable human-reviewed decision trail?

AI SYNERGY HACKATHON 2026

FINAL-ROUND FEATURE SCOPE ADDENDUM
Selected enhancements for the Explainable Grievance Routing & Accountability Assistant
Purpose. This addendum records the selected feature direction and supplements the existing feature-scope and dataset plan. It
does not claim that selected features have already been implemented.
Status rule. “Selected” means approved for consideration/build planning, not implemented. Mark a feature BUILD only
after it works end-to-end and has been tested. Use MOCK for simulated behaviour and ROADMAP for future work.
Safety boundaries retained: no automatic complaint rejection, closure, deprioritisation or duplicate merging. Human reviewers
retain control over consequential decisions. Synthetic data and simulated results must be visibly labelled.
1. Selected feature decisions
Feature
Decision
V1 implementation direction
Speech-to-text
TRY
Citizen records speech; system transcribes it into editable text. The existing
complaint-understanding pipeline processes the confirmed text. Test Hindi, English and Hinglish
with real recordings before making quality claims.
Photo attachment
INCLUDE
Citizen attaches a photo to the complaint. Store securely and show it to authorised staff. No
image analysis, object detection or automatic verification is included.
Hotspot detection
INCLUDE
Flag unusual concentration/increase by area, issue category and time window. Use a table/card
or ranked list; a map is not required. Show period, count, comparison baseline and whether data
is synthetic.
Citizen-side challenge
INCLUDE
Citizen requests review of a suggested department and provides a reason. An authorised

2. Feature design and technical approach
A. Speech-to-text — try
Flow: microphone input → speech recognition → editable transcript → citizen confirmation → existing issue extraction/routing
pipeline. If speech is unclear, ask for confirmation or offer typed input.
Candidate technologies: evaluate OpenAI Whisper as a Python-based option; alternatively assess a cloud speech-to-text API or
browser speech API. Choose after checking language support, setup effort, network requirements, cost/quotas and privacy.
Hindi/Hinglish quality must be tested on representative audio; it is not guaranteed by tool choice.
Acceptance check: test short Hindi, English and Hinglish complaints; review errors on important civic terms, allow transcript
edits, and report observed limitations.
B. Photo attachment — include, without analysis
Flow: select/take photo → validate file type and size → store in private storage → save file reference against complaint ID →
display to authorised reviewer. Do not infer that an issue is verified just because a photo is attached.
Candidate technologies: Next.js/React upload interface, FastAPI upload endpoint, private Supabase Storage (or equivalent),
and a database record linking the file to the complaint. Apply access checks; consider EXIF metadata/privacy and retention.
C. Hotspot detection — no map required
Flow: group complaints by area/ward + issue category + time window → compare current count with a documented baseline →
flag a potential hotspot when a pre-defined rule is met → show counts and time window to staff for review.
Candidate technologies: Python/Pandas or SQL aggregation over PostgreSQL/Supabase data; a transparent threshold or
baseline comparison; a dashboard table/card. Begin with explainable rules rather than complex ML. Choose thresholds using
development data and document them.
Guardrails: missing/approximate locations stay missing/approximate; a hotspot is a signal for investigation, not proof of cause or
negligence. Synthetic data must display a SIMULATED label.
D. Citizen-side challenge
Flow: citizen opens complaint → requests review of department suggestion and gives reason → review item appears in staff
queue → authorised reviewer accepts/changes/escalates → outcome and reason are appended to the ledger.
Candidate technologies: Next.js form/status view, FastAPI request/status endpoints, database fields for complaint ID, challenge
reason, status, reviewer, timestamps and resolution; reuse the decision ledger.

3. Security and model improvement
E. Role-based access control (RBAC) + encryption
Roles: Operator enters/updates permitted complaint details; Reviewer makes authorised routing/review decisions; Auditor reads
history and reports but cannot change decisions in the normal configuration.
Implementation direction: use authentication plus server-side permission checks and database-level access policies where
supported. Hiding a button in the frontend is not sufficient. Test that each role is denied actions outside its permissions.
Encryption: use HTTPS/TLS for data in transit and verify the storage/database provider’s encryption-at-rest settings. Do not
claim encryption is implemented until configuration is checked. Encryption does not replace authentication, access controls,
secure secrets, backups or privacy/retention decisions.
Acceptance check: demonstrate allowed and denied actions for each role; verify unauthorised users cannot fetch protected
complaints/photos; document which platform settings provide transport and storage encryption.
F. Correction-driven model improvement / retraining — staged
Phase 1: save the original suggestion, reviewer correction, reason, timestamp and label provenance. Keep unverified corrections
out of the training set.
Phase 2: once enough verified examples exist and a trainable model is present, run offline retraining on a versioned dataset.
Keep near-duplicates/related cases grouped to prevent train/test leakage.
Phase 3: compare the candidate model with the current baseline on the same frozen held-out test set, including language-wise
errors and abstention. Release only after review; do not retrain/deploy automatically on every correction.
Acceptance check: show before/after evaluation only if an actual training run was completed. Otherwise describe the feature as
correction capture and future improvement workflow.
